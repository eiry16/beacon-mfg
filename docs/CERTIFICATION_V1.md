# 认证流程与灯牌规范 v1

> 配套 `docs/RFQ_V1.md`（询价协议）。本文件定义**供应商怎么从"名录里的一行"变成"客户 Agent 敢下单的对象"**。

## 0. 为什么需要这个

名录（20264 条）解决"能不能找到"，认证解决"敢不敢信"。

数据能抄，**签章抄不走**。但签章要值钱，前提是判定规则公开、可复算、无法手工指定——
否则灯牌就退化成"给了钱的就有"，客户 Agent 三天就会学会忽略它。

因此本规范的第一原则是：

> **灯牌只能由规则算出来，不能直接写进去。**
> 系统里没有 `set_badge` 这种接口，只有 `evaluate`——传入材料，返回"能到几级、还差什么"。

## 1. 分级定义

沿用 `PROPOSAL_V2` §5 的分级，此处补齐可判定的硬条件。

| 等级 | 灯牌 | 含义 | 客户 Agent 呈现 | 可否接自动 RFQ |
|---|---|---|---|---|
| **L0** | 未认领 · 灰 | 自动收录，未经任何核验 | "公开名录，未核验" | 否 |
| **L1** | 已认领 · 蓝 | 主体认证通过，信息由企业自述 | "企业已认领，信息由企业自述" | 否 |
| **L2** | **已认证 · 金** | 营业执照核验 + 材料齐备 + 人工复核 | "平台已认证：营业执照已核验" | **是** |
| **L3** | 已验厂 · 深金 | 第三方实地验厂或客户案例佐证 | "第三方实地核验" | 是 |

**灯牌不是评级。** 它描述的是**信息被核验到什么程度**，不描述这家厂好不好。
对外文案必须带这句限定，规避"平台不做评级"的红线。

## 2. 流程状态机

```
                    ┌──────────────────────────────┐
   apply            │                              ▼
     │         submit_identity            submit_capability
     ▼              │                              │
  applied ────────► │ ───────────────────────────► │
                    ▼                              ▼
              identity_ok                   capability_ok
                    │                              │
                    └──────────┬───────────────────┘
                               ▼
                          review（人工）
                        ╱           ╲
                  approved      rejected
                       │             │
                       ▼             ▼
              L1 / L2 / L3        回到 applied（可补材料重提）
                       │
                       ▼
                    revoked / expired → 降级回 L1
```

### 阶段说明

**Stage 0 · 建档（apply）**
企业名称 + 申报地址进来先查名录：

- **命中**：关联已有 `supplier_id`，走"认领"路径。
- **未命中**：分配新 `supplier_id`（`CN-MFG-{seq:07d}`），走"新建"路径。
  这是常态而非异常——20264 条名录覆盖不到全部制造业企业，
  **企业主动找上门的，本来大多不在名录里**。

**Stage 1 · 主体核验（identity）**
见 §3。

**Stage 2 · 能力核验（capability）**
复用对话式采集的产出。这里不重复问一遍，只做完成度判定。

**Stage 3 · 人工复核（review）**
唯一允许"人"介入的环节，且只做两件事：**看材料是否对得上**、**确认无未决冲突**。
等级仍由规则算，审核员不能指定等级——只能批或不批。

## 3. 判定规则（机器可执行）

### 3.1 L1 · 已认领

全部满足：

1. 联系人手机或邮箱通过验证码（`claim.verified_by` ∈ {wechat, email}）
2. 认证申请里的企业名称，与名录/执照名称**逐字一致**（不含空格与全半角差异）

### 3.2 L2 · 已认证

L1 全部满足，且：

| # | 条件 | 判定方式 |
|---|---|---|
| 1 | 统一社会信用代码格式合法且**校验位正确** | GB 32100-2015，见 §4 |
| 2 | 执照名称 == 申报名称 | 逐字比对（归一化空格/全半角后） |
| 3 | 营业执照材料已登记 | `materials` 含 `business_license` |
| 4 | 无未决的 error 级冲突 | 见 §5 差异处理 |
| 5 | 硬指标完成度 ≥ 60% | 见 §6 |
| 6 | 有一名审核员签字 | `review.reviewer` 非空 |

条件 1-3、5 是机器判定，4、6 是人。
**机器判不过的，压根送不到审核员面前**——省掉的是无效人工。

### 3.3 L3 · 已验厂

L2 全部满足，且满足其一：

- `evidence.field_audited` 非空（第三方验厂报告已登记），或
- 客户案例佐证 ≥ 2 条且至少 1 条可公开查证

### 3.4 降级与吊销

- **L2/L3 有效期 12 个月**。到期未复核 → 自动降 L1，不静默保留。
- 发现材料造假 → `revoked`，且**永久记录**（企业可重新申请，但历史留痕）。
- 降级/吊销后，已发出的能力卡 `claim.badge` 同步改写——**不存在"卡上是 L2、实际已吊销"的中间态**。

## 4. 统一社会信用代码校验（GB 32100-2015）

18 位。前 17 位本体码 + 第 18 位校验码。

- 字符集：`0123456789ABCDEFGHJKLMNPQRTUWXY`（31 个，**不含 I O S V Z**）
- 加权因子（前 17 位）：`1,3,9,27,19,26,16,17,20,29,25,13,8,24,10,30,28`
- 校验码：`C = 31 - (Σ(Ci × Wi) mod 31)`，若 `C == 31` 则 `C = 0`

**校验位通过 ≠ 企业真实存在。** 它只证明这串字符不是随手敲的。
主体是否真实存在，靠人工比对执照材料——这是 §3.2 条件 3 和 6 存在的理由。

## 5. 差异处理（最重要的一节）

公开记录之间经常互相矛盾，申报信息与公开记录也经常对不上。
**矛盾本身不是拒绝理由，未解释的矛盾才是。**

差异分三级：

| 级别 | 含义 | 处理 |
|---|---|---|
| `info` | 不影响主体判断（如电话是旧号） | 记录，不阻断 |
| `warning` | 需留意（如员工人数与规模区间不符） | 记录，不阻断，提示审核员 |
| `error` | 影响主体判断（如地址与全部公开记录不符、名称不一致） | **阻断**，需企业解释 |

企业可对每个 error 提交解释（`explain`）。解释后差异转为 `explained`：
**仍是差异，但不再是阻断项**，且对客户 Agent 可见——
`identity.address_note` 会写明"企业申报地址与 2025 年报地址不一致，企业说明：新厂搬迁"。

> 这样处理的理由：企业搬迁、执照变更、年报滞后都是**真实且常见**的。
> 一刀切拒绝会误杀真实企业——正是项目要避免的"因为标签问题让 40% 名录搜不到"。

### 地址核验的具体做法

平台不做"真伪判定"，只做**交叉比对**：
把公开查到的地址记录（带 `source` 与 `confidence`）登记为输入材料，
与申报地址比对，产出相似度与差异列表。判定权在人工复核。

比对维度：省 / 市 / 区 / 路名 / 门牌号。
**区级不匹配判 error，路名或门牌不匹配判 warning 并要求解释。**

## 6. 硬指标完成度

完成度 = 已填字段数 / 适用字段数，按权重加权：

- `limits.*`（硬边界）：权重最高——客户 Agent 主要靠它淘汰供应商
- `processes`、`materials`：次之
- `service.*`：最低

**未填 ≠ 不做。** 未填字段降权保留，不淘汰（沿用项目既有红线）。
完成度只影响灯牌门槛，不影响名录可见性。

## 7. API

| 端点 | 说明 |
|---|---|
| `POST /v1/certify/apply` | 建档（命中则关联，未命中则新建 ID） |
| `POST /v1/certify/{app_id}/identity` | 提交主体信息，返回逐条核验结果 |
| `POST /v1/certify/{app_id}/explain` | 对 error 级差异提交解释 |
| `POST /v1/certify/{app_id}/capability` | 登记能力数据（含完成度） |
| `POST /v1/certify/{app_id}/review` | 人工复核，规则算等级 |
| `GET  /v1/certify/{app_id}` | 申请详情与当前状态 |
| `GET  /v1/certify/{app_id}/badge` | 灯牌试算：**还差什么才能升级** |
| `GET  /v1/certify` | 按 supplier_id / status 检索 |

全部写入端点要求 Bearer 凭证。存证落 `server/.data/certification/`。

## 8. 红线

1. **不编造。** 查不到就 `null` 并标 `awaiting_evidence`，不用"看起来合理"的值填空。
2. **灯牌不可指定。** 只有 `evaluate`，没有 `set_badge`。
3. **公开记录要标来源。** 每条 `public_record` 必带 `source` 与 `confidence`，
   不同来源互相矛盾时不合并成"事实"，并列保留。
4. **弱证据不覆盖强证据。** 自述 > 公开记录 > 名录推断，顺序不可颠倒。
5. **草稿不外发。** `mode=fixture` / 未通过复核的卡，不进入对外检索结果。
