一、现状：先说清楚三个硬约束

动手设计前，我把现有资产和坑摸了一遍。有三个事实会直接决定方案走向：

1.1 采集引擎已经很完整，但"云端"不存在

server/routers/collect.py（527 行）已经是一套完整的状态机采集引擎：5 组题目（基础信息 / 能力 / 硬指标 / 质量 / 商务），口述风格提问（"咱们是哪年开的？"），normalize.py 做确定性归一化（"一丝" → 0.01mm），会话可跨请求跨天继续。API 也齐了：

我在 App 侧做的 HEAD 探活只是止血，让采购看到一句人话而不是 404 页面。真正的修法是先把云端存储建起来，这是下面所有事的前置。

1.2 App 侧零写入能力

ToolBox.definitions() 只注册了 search_suppliers / get_supplier_detail / list_categories 三个只读工具。没有 HTTP 写入通道，没有供应商身份，collect 的 require_operator 目前只是把 Bearer token 做个 sha256 当指纹。

1.3 人脸是法律高压线，不是技术选型

这条最重要，先摆事实（《人脸识别技术应用安全管理办法》，2025-06-01 施行）：

条款要求对本项目的含义
第 10 条存在其他非人脸方式可实现同等目的的，不得将人脸识别作为唯一验证方式必须提供不刷脸的替代路径
第 8 条人脸信息应存储于本地设备或境内服务器并加密；通过互联网对外传输须取得单独同意不能自己收图像传云端
第 6 条需取得个人在充分知情下自愿、明确作出的单独同意不能混在用户协议里打勾
第 11 条应用前须进行个人信息保护影响评估（PIA）并记录上线前要出一份 PIA
第 15 条处理人脸信息达到 10 万人须 30 个工作日内向省级以上网信部门备案短期不触发，但架构要留口

结论：BeaconMFG 一行人脸图像都不该碰。正确姿势是让第三方核身服务商（腾讯云慧眼等）在自己的 SDK 里完成采集、活体、比对，只把结论（通过/不通过、比对分数、流水号 BizToken）回传给我们。我们存的是"这家企业的法定代表人于某时通过核身，流水号 XXX"，不是任何一张脸。这样上面第 8、11、15 条的压力全部落在有资质的服务商身上，我们只承担"接收并妥善保管结论"的责任。

三、身份切换设计

3.1 为什么必须物理隔离，而不是加几个工具

最省事的做法是在现有 ToolBox 里加几个写入工具。我不建议，理由：

  • 误触发风险。采购问"上海做输送线的厂"，模型手上有 submit_capability，就有概率调错。写入操作调错的代价比读操作大得多 —— 它会污染数据。
  • 提示词打架。采购侧提示词反复强调"不编造数字、如实说明证据档位"；供应商侧要的是"鼓励他把话说完、帮他补全"。两套人格塞进一段 system prompt，两边都做不好。
  • 攻击面。买家端平白多出写入接口，纯属自找麻烦。

所以：两套 system prompt、两套工具集、一次只加载一套。切换身份 = 重建 ToolBox 实例 + 清空会话（明确提示用户"切换身份会开始新对话"）。

两条实现后修正的设计（原稿写错了，以代码为准）：

① 路由前缀写错了：claim.py 是 APIRouter(prefix="/claim")，没有 /v1（collect 才有 /v1/collect）。照原稿的 /v1/claim/verify-start 写会直接 404。

② 内部句柄不给模型：session_id / supplier_id 一律由 App 自己记，不作为工具参数暴露。实测暴露给模型后，它拿不到值就自己猜——把 supplier_id 当 session_id 传回来，服务端回 INVALID_SESSION。状态归状态机管，模型只管说话。

③ 每轮必须回灌平台状态：模型的 tool_choice=auto 会不调工具直接说「记下了」然后自己编下一题（平台一步没动），也会跳步骤（跳过验证码直接调采集）。所以每轮系统提示词都附「认领走到哪一步 / 采集当前是哪一题 / 必须提交」，并且这一轮真没提交时界面如实标红。

四、对话式采集：嘴脑分离

这是整个方案的技术核心，也是我最想和主人确认的一点。

4.1 陷阱：不能让 LLM 自己掌管 30 题

直觉做法是给 LLM 一份 30 题清单，让它自己问完。这条路走不远：

  • 会漏题、会重复问。LLM 没有可靠的位置记忆，聊到 20 题以后基本在乱走。
  • 上下文爆炸。30 轮往返 × 每题几百字，后期每轮都在烧 token，延迟和成本都失控。
  • 归一化不能靠猜。"一丝"、"一个道"、"头发丝的三分之一" 都是 0.01mm 量级的说法，normalize.py 里是确定性规则 + 词表。让 LLM 归一化等于把硬指标交给概率 —— 这直接违反项目"不编造数字"的红线。

4.2 正解：状态机掌管一切，LLM 只做翻译

已有的 collect 引擎就是那个状态机。分工：

状态机（脑）· 已有

决定问第几题（ses.i 指向 flat 列表）

接受答案 → normalize_field() 确定性归一化

检测冲突（ses.conflicts()）

算完整度、判必填是否齐

落盘、跨天续聊

LLM（嘴）· 新增一层

把干巴巴的题面改写成口语，带一点共情和举例

把供应商的口述抽成结构化片段交给状态机

识别"这题我不会" / "回头再填" / 答非所问

不碰进度、不碰归一化、不碰冲突

一次往返长这样：

供应商: "大概一丝吧，精加工能做到半丝"

  ┌─ LLM（嘴）：提取，不判断
  │   → {"tol": "0.01", "note": "精加工可达 0.005"}
  └─ 交给状态机

  ┌─ 状态机（脑）：确定性处理
  │   normalize("0.01") → tol = 0.01mm
  │   与上一题"最大件 800×600"做冲突检测 → 无 error
  │   ses.i++ → 下一题「做一百件呢？」
  └─ 返回下一题题干

  ┌─ LLM（嘴）：把题干说成人话
  │   "那做一百件的话大概要几天？"
  └─ 输出给供应商

LLM 挂了怎么办？直接把状态机的原始题干吐出来——"打个样要几天？" 照样能问完。采集流程对 LLM 是软依赖，这是稳定性的关键。

4.3 题面改写的具体要求

给 LLM 的改写提示词要写死几条（沿用项目"不编造"纪律）：

  • 不许替供应商回答。不许出现"您应该是 2010 年建厂的对吧？"这种引导。
  • 举例只能是题干里自带的 hint。状态机给的 hint 是"例：五天"，LLM 可以说"比如五天"，但不能自己发明"像贵司这种规模一般七天"。
  • 一次只问一题。人话可以铺垫，但不能顺手把后面两题也问了 —— 状态机一次只接一个字段。
  • 没听清就再问一遍，不许猜着填。猜出来的进 self_declared 就是污染。

五、存储：分层，且 Git 降级为发布快照

主人问"资料是否也挂云端储存" —— 答案是必须，而且今天这个 404 就是不用云端的代价。但不能所有东西一股脑丢上去，要分层。

层内容存储位置公开性进 Git？
L0 指纹最小字段 ~120B云端 DB → 导出 jsonl公开，供 Agent 全量扫描是（发布快照）
L1 能力卡结构化硬指标云端 DB（唯一真源）公开是（快照副本）
L2 自述SKILL.md云端 DB公开是（快照副本）
证照原件营业执照、ISO 证书扫描件私有对象存储不公开，签名 URL + 有效期否
核身记录姓名、证件号（加密）、BizToken、结论独立加密库绝不公开，访问审计否
会话态未完成的采集会话云端 DB不公开否

5.1 关键改动：Git 从"真源"降级为"快照"

现在是反的 —— 产物直接写进仓库目录，能不能被外界看到全看它进不进 Git。改成：

供应商提交 ──写──> 云端 DB（立即可见，唯一真源）
                        │
                        │ 定时任务（每小时 / 每次 confirm）
                        ▼
              生成快照 ──commit──> Git ──> Pages ──> CDN（只读副本）

好处：供应商提交完立刻在 App 里能看到自己的卡，不用等下一次部署；CDN 仍然是公开只读副本，Agent 该怎么扫还怎么扫。今天的 404 从根上消失。

5.2 选型建议

项目现在是纯静态 + FastAPI，建议别上来就上重家伙：

  • 结构化数据：Cloudflare D1（账户内 SQLite 兼容 Serverless DB）。能力卡字段不固定，主表用 JSON 列存 data，同时把检索要用的字段（gb 码、city、cl、tel、updated_at）提成真列建索引。会话态放同库的 collect_session 表（用 Pages Functions 的 D1 binding 调用，零外部依赖）。
  • 证照/原件：Cloudflare R2（对象存储，出口流量免费，同生态一个账单）。私有 bucket，App 侧拿签名 URL，有效期 15 分钟。
  • 核身记录 / 临时凭证：Cloudflare KV（带 TTL 的最终一致 KV）。验证码 5 分钟过期，BizToken 30 分钟过期；电子营业执照核验结论单独存一行审计记录，密钥走 Workers Secrets。
  • 核身记录：D1 单独 schema + 列级加密，密钥走 Workers Secrets，不和主库共用账号。

为什么不用 Supabase / Postgres：主人手里已经有 Cloudflare 账户和 API Token，Pages 项目也已存在。R2/D1/KV 全在同一个账单、同一个身份下、同一个 API Token 调通——一份 Token 覆盖 90% 的存储需求，**不需要再开第二个 SaaS 账号**。这点主人拍板时专门点了出来：

"这个里面的 skill 没有了？如果能存 skill，难道不能存供应商的认证资料？看看是否可行，是否一定要用 Supabase？"

答：Cloudflare Pages 不只是静态站点托管，背后挂了 R2（对象）/ D1（SQLite）/ KV（带 TTL）/ Workers（函数运行时）。skill 既然能存，认证资料同样能存，**且都在一个账户、一份 Token、一个账单下**。

一条纪律：证照原件永不公开。能力卡里只记"已提交营业执照并通过核验"这个事实和材料 ID，不放大图、不放可直链的文件地址。采购能看见"有"，不能看见"是什么"。这既是保护供应商商业秘密，也避免我们变成证照泄露的源头。

六、身份验证：分级，且不急着刷脸

不要一上来就上人脸。按灯牌等级分三级，每一级解决不同的问题：

等级要证明的事手段成本人脸？
L1 已认领这个手机号/人确实在这家企业手机号验证码 + 统一社会信用代码匹配名录≈0否
L2 已认证操作人是法定代表人本人营业执照 OCR 核验 + 法定代表人核身≈1 元/次是（第三方）
L3 已验厂现场真实存在、产能属实第三方验厂 / 视频验厂数百元/次否

6.1 L2 的三条路径（按推荐度排序）

路径 A：电子营业执照扫码授权 免费 有资质门槛

市场监管总局官方的"电子营业执照"微信/支付宝小程序，法人在下载执照时已经做过人脸识别。它支持"扫码登录"：我们的系统出示一个二维码，法人用小程序扫一下并确认，我们就能拿到"这家企业的法定代表人刚刚授权了"这个结论。

对我们来说这是最优解：权威源是国家市场监管总局，我们零接触人脸数据，成本为零。

门槛：需要公司主体资质。接入需向省级市场监管部门提出申请，填写《电子营业执照应用接入信息表》并签订数据共享保密协议，省局内部审批后报市场监管总局备案；跨省应用还需省局向总局申请。

2026-09-10 主人拍板：主人确认已有公司主体，愿意去申请电子营业执照开放平台接入。P3 不再卡资质，可以做。立即启动的步骤（详见本文 §6.3）：

  1. 法人本人微信 → 搜「电子营业执照」小程序 → 法人本人登录（这一步会做人脸核验，法人在下载执照时已经做过人脸，我们零接触）；
  2. 小程序内 →「开放平台」→「第三方应用接入」；
  3. 提交《电子营业执照第三方应用接入申请表》+ 营业执照扫描件 + 对公账户（小额打款验证 0.01–0.99 元随机金额）+ 技术对接人身份证；
  4. 回调地址填 https://<pages>.pages.dev/claim/callback（P2 阶段建）；
  5. 5–10 个工作日审核通过，拿到 AppID + AppSecret；
  6. 用 AppID 调 /api/v1/qualification/getEntInfo 验真，字段：统一社会信用代码、企业名称、法人姓名（只用于核验不入库，核完即弃）、注册地址。

与 P0 的关系：电照接入依赖 P2 的 callback 路由，因此建议 P0 → P1 → P2 → P3 串行推进，但 P3 的资质申请（P2/P3 之间）和 P1/P2 的代码可以并行启动，不等审核通过。

假设 1000 家供应商走 L2：约 740 ~ 1500 元，对冷启动不算压力。

接入姿势（这决定了合规与否）：

  • 用慧眼 H5/小程序 SDK，采集、活体、比对全在腾讯侧完成。
  • 我们只接收 BizToken + 结果码 + 比对分数。不要求原始图像、不要存照片、不要存视频。
  • 数据库里存的是一条审计记录：{supplier_id, 核身时间, BizToken, 结论, 分数}。

路径 C：人工兜底 免费 法律强制要求

《人脸识别技术应用安全管理办法》第 10 条要求：存在其他非人脸方式可实现同等目的的，不得将人脸识别作为唯一验证方式。所以下面这条路必须存在，不是可选项：

  • 上传营业执照 + 加盖公章的授权书 → 人工审核 → 判 L2
  • 或对公账户小额打款验证（回填金额）

界面上必须给出"刷脸验证"和"其他验证方式"两个并列入口，不能把刷脸前置为默认。

6.2 人脸相关的三条铁律（写进代码注释那种）

  1. 我们绝不采集、传输、存储人脸原始图像。只存第三方返回的流水号与结论。
  2. 人脸永远不是唯一路径。任何核身入口旁边必须有等效的替代方式。
  3. 单独同意。核身前弹独立授权页，说清"为什么需要、由谁处理、存多久、如何撤回"，不能和用户协议合并打勾。撤回同意后删除对应记录（BizToken 保留做审计，不保留结论）。

9.1b 顺手修掉的两个坑

实测教训：Cloudflare API 有速率限制，并发调高会撞死（2026-09-10 16:35 亲测）。

第一次全量上传用了 12 并发，12411 个文件里成功 4543、失败 7868，失败原因全部是 HTTP 429，耗时 942 秒只完成 37%。免费账户约 1200 请求/5 分钟，并发一高就从某个点开始全程被拒，剩下的全白跑。

修法（已写进 publish_r2.py）：

  • 并发从 12 降到 4
  • 429 / 5xx 指数退避重试（1→2→4→8→16 秒），服务端给 Retry-After 就听它的
  • 默认跳过已存在的对象，只补传缺失的（--no-skip 可强制覆盖）

宁可慢一点一次跑完，也不要「一半成功一半失败」的半成品 —— 那种结果最难收尾。

P0 唯一外部依赖：R2 在 Dashboard 启用（10 秒）+ 新 Token 加 D1/R2/KV 权限（5 分钟）。其余全是本地代码，今晚就能起跑。
