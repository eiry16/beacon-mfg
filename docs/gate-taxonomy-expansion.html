主人四项拍板（已按此实施）： ① 单池多门类，ID 带门类字母（CN-H-0001234，制造业保留历史前缀 CN-MFG-）； ② 农林水产只建框架、暂不填数； ③ 首个验证门类选餐饮（H）； ④ 每个门类独立 schema，互不共用。

二、数据源现实：先讲清楚，否则会变成「凑数」

现有 23,823 家全部来自高德 POI（scripts/fetch_gaode_poi.py），入库时靠 AMAP_TYPE_POSITIVE = 工厂|制造|工业 过滤，再用公司名特征词推断品类。换门类就是换数据源，每个门类的可得性差别极大 —— 这决定了分期顺序，不是拍脑袋排的。

三、架构：共享信封 + 门类私有 schema

主人选了「每个门类独立 schema，互不共用」。我完全同意 —— 但独立 schema 有个必须补的前提，否则 L0 指纹和检索层会被迫按门类分叉。那个前提就是信封（envelope）必须共享。

skills/schema/
├─ envelope.json          ← 共享信封：全门类字段名与语义逐字一致
├─ gates/
│   ├─ C.json             ← 制造业私有：processes / 公差 / 最大工件尺寸 / PPAP
│   └─ H.json             ← 餐饮私有：菜系 / 席位 / 包间 / 宴会厅（没有 processes）
├─ cap-codes/
│   ├─ _registry.json     ← 能力码表域注册表（manufacturing / restaurant / …）
│   └─ restaurant.json    ← 餐饮码表：菜系 34 + 服务形态 13 + 场地 7 + 时段 6
└─ process-codes.json     ← 既有 43 条工艺码，正式登记为 manufacturing 域（零迁移）

scripts/gate_schema.py    ← 运行时装配器：信封为基底，门类 schema_extra 逐键覆盖
1
装配：信封当基底，门类赢_deep_override()：业务键按门类覆盖；properties 逐键合并；required 取并集。顶层 additionalProperties: false 让独立性成为硬约束 —— 餐饮卡带上 capability.cuisines 会被制造业 schema 拒绝。
2
枚举注入：码表是唯一真源门类 schema 里写 x-enum-from: "restaurant:菜系"，装配时从码表注入 enum。菜系清单只存在于 cap-codes/restaurant.json 一处，不在 schema 里重复一遍。
3
caps_index：独立与统一之间的桥每个门类自己写 caps_index_from 表达式（制造业导出工艺码、餐饮导出菜系/场地/时段码），derive_caps_index() 算出扁平字符串数组。L0 指纹与检索层只读这个字段，永不解析门类私有块。
4
采集问句分层STEPS_HEAD（通用：谁、多大、在哪）+ STEPS_BY_GATE（门类主体）+ profile 字段 + STEPS_TAIL（询价通道 + 主动声明边界）。同一个字段在门类间换措辞用 label_by_gate / question_by_gate 覆盖，不覆盖时用默认值 —— 而 C 的默认值就是改造前原文，所以制造业问句一个字节都没动。

为什么不拆成两份独立数据？「营业面积 / 厂房面积 / 门店面积 / 用地面积」是同一个语义（能承接生意的物理空间），只是叫法不同。拆成字段就意味着检索层要按门类分支，而这正是本次改造要消灭的东西。所以：私有块可以完全不同，信封字段必须逐字相同。

3.1 信封里放了什么

envelope.json 定义 supplier_id（^CN-(MFG|[A-Z])-[0-9]{4,7}$）、gate（A–T 枚举）、category、gb_code/gb_name/gb_path/gb_level、identity、contact、limits、rfq、exclusions、not_applicable、claim、evidence、safety、provenance、caps_index。

三个刻意的设计决定：

  • rfq 放在信封层，不放门类层。它是客户 Agent 把询单送进来的传输协议，不是供应商的业务能力。protocol 枚举含 email/webhook/mcp/form/wechat/phone —— 餐饮门类默认走 phone，制造业默认 email，但契约只有一份，下游投递逻辑不用按门类分叉。
  • 必填项只放「已有、或能无损耗推导」的字段。gate 由 ID 前缀推导，caps_index 由表达式派生，两者都是确定性的，写入时补即可。故意不放进必填：exclusions（旧卡从未被问过这一题，强制必填等于逼人编造）、safety（旧 schema 只约束了子字段，没有顶层必填）。
  • business_nature 扩了三档：service_provider / individual / farm —— 原来的 manufacturer / trader / mixed 只覆盖制造与流通。

3.3 POI → 国标映射（餐饮为什么准）

制造业靠公司名特征词推断品类，因为工厂名里有「精密机械」「模具」这类强信号。餐饮几乎相反 —— 「川味小馆」「老王饭店」里根本没有菜系信息。但高德的 POI 类目是平台自己标的，比公司名可靠得多。所以 gates/H.json 带了一张前缀匹配表：

"餐饮服务;中餐厅"        → 6210 正餐服务
"餐饮服务;快餐厅"        → 6220 快餐服务
"餐饮服务;咖啡厅"        → 6232 咖啡馆服务
"住宿服务;民宿"          → 6130 民宿服务
"住宿服务;宾馆酒店;五星级宾馆" → 6110 旅游饭店

拿不准的不猜，进 ambiguous 列表并让 gb_code 留 null，交给采集时确认。例如：

  • 餐饮服务;糕饼店 —— 前店后厂：主体可能是零售（F52），也可能是食品制造（C14），要看营业执照经营范围。
  • 餐饮服务;小吃店 —— 小吃服务是 6291，但高德把很多正餐店也标成小吃店，名录侧不可靠，需采集时确认。

四、端到端样本：餐饮

examples/gate-expansion-H/ 是一张完整跑通的餐饮卡（示例数据，provenance.mode = fixture，不得对外发布）。它证明了整条链路：

1
会话POST /v1/collect/session {supplier_id: "CN-H-0000001"} → 门类由 ID 前缀回判为 H，加载餐饮问句集（10 个必填，不多于 C）
2
作答归一化「川菜和湘菜」→ ["cuisine_sichuan","cuisine_hunan"]；「能办宴席」→ svc_banquet；「有停车场」→ venue_parking。「不收定金」→ deposit_required: false（false 是有效答案，不是未填）
3
定稿渲染派发到 H 渲染器，产出 L1 能力卡（含 caps_index）+ L0 指纹行 + L2 SKILL.md（8 段，全文无制造业术语）
4
校验按卡片自己的门类选 schema 验证；caps_index 与派生值不一致就硬失败

L0 指纹（一条 ~120 字节，给客户 Agent 全量扫）泛化成了门类中立的形状：

{"id":"CN-H-0000001","co":"…","g":"H","city":"上海市",
 "cap":["cuisine_sichuan","cuisine_hunan","svc_banquet","venue_parking","time_lunch", …],
 "proc":[], "seat":180, "pp":150.0, "cert":["食品经营许可证","HACCP"], "sc":70}

proc 保留为空数组（餐饮没有工艺），新增 g（门类字母）、cap（跨门类能力码）、seat（席位）、pp（人均）—— 检索层读的还是同一批字段，不需要知道门类细节。

顺手抓到并修掉的真实缺陷

P2 的价值不只在新门类。写测试的过程把几个**不报错、只是悄悄改错数据**的问题翻了出来 —— 这类问题比崩溃难发现得多，也正好都踩在「数据宁可留空也不编造」这条红线上。

问题后果（不修的话）
